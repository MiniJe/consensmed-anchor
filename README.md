# ConsensMed Verify

Publicly verifiable authenticity for medical documents, with no medical data on-chain.

A clinic issues a document (a letter, a summary, a certificate). Later, someone else holds a copy: a patient, an insurer, another clinic. ConsensMed Verify lets that person check, without calling the issuer and without an account, that the file is exactly the one that was issued and that it has not been revoked or replaced since.

Built for the Arbitrum Open House buildathon. It runs on Arbitrum Sepolia (testnet).

## The problem

A PDF proves nothing about itself. Anyone can edit one, and a document that was correct when issued may have been withdrawn or corrected afterwards. Today the only way to know is to ask the issuer, which is slow, depends on the issuer being reachable, and usually means sharing the document again.

## How it works

Each document gets two values:

- **`docId`**: 32 random bytes, generated by the issuer before the document is finalised and printed in the document as a QR code. It carries no meaning.
- **`contentHash`**: the SHA-256 of the final file, byte for byte.

The issuer registers the pair on-chain. The registry then answers one question, `verify(docId, contentHash)`, with one of five states:

| State | Meaning |
|---|---|
| `VALID` | This exact file is the registered document and it is in force. |
| `MISMATCH` | A document with this ID exists, but this file is not it: altered, or a different file. |
| `REVOKED` | This is the registered document, and the issuer withdrew it. |
| `SUPERSEDED` | This is the registered document, and the issuer replaced it with a newer one (the registry points to it). |
| `NOT_FOUND` | The registry has no such document. |

The random `docId` solves a circular problem: the QR code has to be inside the file, so it cannot contain the hash of that file. The ID exists first, the file is built around it, and only then is the file hashed.

Revocation and replacement are why a chain is useful here rather than a plain list of hashes: the state of a document changes over time, and anyone can read the current state without trusting or reaching the issuer.

## Verify a document

1. Scan the QR code on the document, or open the [verification page](https://minije.github.io/consensmed-anchor/verify/).
2. Choose the file.

The page computes the SHA-256 in your browser and reads the contract through the public Arbitrum Sepolia RPC. The file is never uploaded. Without a QR code the page looks the document up by its fingerprint (`docIdOf`).

You do not need the page at all. The same answer comes straight from the contract:

```bash
cast call 0x6F0aDfD3ef7befac17A6165A9Db07BFd54C2d285 \
  "verify(bytes32,bytes32)(uint8)" <docId> 0x$(sha256sum document.pdf | cut -d' ' -f1) \
  --rpc-url https://sepolia-rollup.arbitrum.io/rpc
```

The result is the state index: 0 `NOT_FOUND`, 1 `VALID`, 2 `MISMATCH`, 3 `REVOKED`, 4 `SUPERSEDED`.

## What is on-chain

Per document: the random ID, the SHA-256 fingerprint, the issue time, the state, the ID of the replacement if there is one, and the address that issued it. Nothing else. The contract has no text or free-form fields at all, so names, diagnoses and identifiers cannot be written to it even by mistake. See [docs/THREAT-MODEL.md](docs/THREAT-MODEL.md) for what this does and does not guarantee.

## Run the contract tests

Requires [Foundry](https://getfoundry.sh). Dependencies are installed locally and are not tracked in this repository.

```bash
cd contracts
forge install --no-git foundry-rs/forge-std@v1.17.0 OpenZeppelin/openzeppelin-contracts@v5.7.0
forge test
forge coverage --report summary
```

## Run the demo

The demo builds synthetic PDF documents with a QR code and walks them through the registry: issue, verify, alter one byte, revoke, replace. It needs Foundry (`cast`), Node 20 or newer, and the key of an address that is an authorised submitter on the contract, present in the environment as `ARB_SUBMITTER_KEY`. Use a testnet-only key.

```bash
cd demo
npm install
node make-demo.mjs            # issues the documents and prints the five states read back from the contract
node make-demo.mjs --reissue  # tries to issue the original again; the registry refuses
```

Outputs go to `demo/out/`, which is not tracked. The documents contain synthetic data only and say so on the page.

The deployed contract accepts documents only from its own submitter. To run the demo end to end with your own key, deploy your own instance and point the demo at it:

```bash
cd contracts
forge script script/Deploy.s.sol --rpc-url https://sepolia-rollup.arbitrum.io/rpc --broadcast
export ARB_ANCHOR_CONTRACT=<address printed by the script>
```

The public page reads the contract listed above, so documents issued on another instance are checked with `cast call` as shown earlier.

## Limits

- Testnet only. Nothing here has been audited.
- One key is both owner and submitter in the demo deployment. A real deployment separates them.
- The registry shows that a file is the one an address registered. It does not show that the content is true, or who stands behind that address.
- One transaction per document; no batching.
- The integration with the ConsensMed platform is private and is not part of this repository.
